CS Expectations

Build. Explain. Rebuild. Submit Evidence.

This course is not about “I watched the video.” It is about proving that you can create, understand, and improve real computing work.

Learning = visible output + clear explanation + honest process.

01 · Mindset

CS is a developer-style course.

You do not pass by listening. You pass by building something that works and explaining how it works.
01

Build

Create working projects, not isolated screenshots.

02

Explain

Use correct technical language to describe your code and decisions.

03

Improve

Debug, revise, commit, and rebuild without depending on a full solution.

02 · Core Goal

Turn a trained ML model into a web app.

The long-term CS target is to connect machine learning with real software: train, evaluate, build an interface, and let people use it.

MODEL → APP
The final product is not just a notebook. It is a usable web application with a clear purpose.
  • Train or use an ML model for a clear task.
  • Evaluate whether the model works well enough.
  • Wrap the model with a simple backend or API.
  • Build a frontend interface for real users.
  • Deploy or share the app with documentation and evidence.
Core target: AI learning + web development + visible product evidence.
03 · Class Flow

The CS learning cycle

Every lesson follows a repeatable workflow. The goal is mastery, not temporary completion.

Step 1Entry Point CheckShow readiness. Recall prior concepts.
Step 2Individual LearningWatch, read, code, and take notes.
Step 3Talk RobinExplain your understanding to peers.
Step 4Teacher ClarificationFix misconceptions and connect ideas.
Step 5Mission TaskBuild the required product.
Step 6Independent RebuildRedo key parts without full-solution reference.
Step 7Evidence SubmissionSubmit repo, screenshots, commits, reflection.
Step 8Oral CheckExplain what you built and why it works.
04 · Definition of Done

“It runs” is not enough.

DONE
A finished mission has working output, clean evidence, and a student who can explain the work.
  • The app or program runs correctly.
  • The required features are implemented by you.
  • The README explains purpose, setup, and usage.
  • GitHub commits show meaningful progress.
  • You can make a small change without copying a full answer.
  • You can explain the key concepts orally.
05 · Evidence Pack

Every mission needs proof.

Your evidence is your learning record. No evidence means the work cannot be verified.

Required evidence

  • GitHub repository or folder link
  • Running app screenshot
  • Commit history screenshot or link
  • Course progress / learning resource evidence

Reflection evidence

  • What did you build?
  • What concept did you learn?
  • What bug or difficulty did you face?
  • What would you improve next?
06 · GitHub Standard

Commit history matters.

GitHub is not just storage. It is a professional record of how your project grows.

Good commits

  • Add React component structure
  • Fix Vite startup error
  • Update README with run instructions
  • Refactor JSX layout

Weak commits

  • update
  • final
  • stuff
  • homework done
A strong student leaves a clear technical trail.
07 · AI & Tutorial Policy

Use help. Do not outsource thinking.

Allowed

  • Ask AI to explain an error message.
  • Use tutorials to learn syntax and patterns.
  • Ask for hints, examples, or debugging strategies.
  • Use a personal checklist during rebuild.

Not allowed

  • Copy a complete solution as your own.
  • Submit AI-generated code you cannot explain.
  • Open full-solution references during independent rebuild.
  • Hide outside help in your reflection.

You must understand every key line you submit.

08 · Independent Rebuild

Rebuild proves mastery.

If you can only finish while looking at the answer, you have completed a tutorial — not learned the skill.

Close

Close full solutions and copied reference code.

Recreate

Rebuild the core structure using memory, notes, and checklists.

Explain

State what changed, why it works, and what still feels unclear.

10 · IOAI Focus

IOAI is the top target.

Why IOAI matters
AI + CS

  • It matches the future direction of this course: AI, data, and real computing.
  • It rewards students who can learn beyond the textbook.

  • It requires both theory and implementation, not only memorization.
  • Students preparing for IOAI should keep a visible GitHub / portfolio record.

12 · Competition Evidence

Award claims must be verifiable.

To apply the A+ Competition Policy, submit official and technical evidence.

  • Official certificate, medal, ranking page, or organizer confirmation.
  • Competition name, level, date, and award category.
  • Code, notebook, report, design document, or project link when applicable.
  • Clear explanation of your personal contribution, especially for team events.
  • Short reflection: what you learned, what was difficult, what you would improve.
  • Academic honesty: no plagiarism, hidden outsourcing, or fake evidence.
13 · Conditions

Award ≠ free pass.

The policy is generous, but it is not an excuse to ignore class work.

  • All competition rewards require serious regular class participation.
  • You still submit required GitHub, portfolio, and reflection evidence.
  • You maintain academic honesty: no plagiarism, no hidden AI outsourcing.
  • The competition must be clearly related to CS, AI, robotics, cybersecurity, or computing.
  • You provide official proof: certificate, ranking, competition page, or submission record.
  • You can clearly explain your own work, especially for team competitions.
  • Participation bonus requires verified registration, preparation, and submission evidence.
